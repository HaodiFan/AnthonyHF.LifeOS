# 知识抽样问题库（Knowledge Probes）

「问心」的防伪最后一道防线。当用户在某领域的水位**看起来 ≥ L4 但有可疑信号**时，从这里抽 1-2 题问 ta，验证实际知识。

## 设计原则

### 1. 这不是考试

**关键心法**：知识抽样是**信号确认**，不是**能力测试**。

- 答得上来 → 印证 L4+ 水位
- 答不上来 → **不一定**是 L4 不到，可能只是**时间距离**导致的遗忘
- 答得"漂亮且自如" → 真壁垒
- 答得"对但生硬" → 实力存在但鲜度低

**永远 1-2 题，不要 3 题以上**。3 题以上会让用户感觉被审讯，破坏信任关系。

### 2. 时间距离敏感（Time-distance Sensitivity）⭐

问题难度必须根据用户**最近一次实际接触该领域的时间**动态调整。

| 时间距离 | 应该问 | 不应该问 |
|---|---|---|
| **近期（1-2 年内）** | 具体函数名、参数、性能数据、踩过的坑 | 太粗的概念题（侮辱专家） |
| **中期（3-5 年）** | 框架级问题、架构选择、权衡、设计模式 | 具体 API、具体语法（不公平） |
| **远期（5 年以上）** | 核心思想、判断、宏观决策、原理对比 | 任何具体实现细节（在测记忆力，不在测能力） |

**违反这条原则的评估全部无效**——一个离开某领域 8 年的 CTO 答不出最新框架的 API，**不能否定** ta 当年在这领域是 L5。

### 3. 触发条件

不是每次都做。**只在以下情况触发**：

- 用户在某领域水位估算 ≥ L4，**且**：
  - 用户的关键词陈述"过于顺畅"——像是反复练过的稿子
  - 四维密度校准有可疑信号（比如时间利用率很低但水位很高）
  - 用户自述的项目细节和该领域的实际工作内容**对不上**
  - 用户使用了行业内**生疏感很重**的术语（用错或用得不自然）
- 用户主动要求"测我一下"
- 用户的领域和 ta 的整体轨迹**不一致**（比如做产品的人突然说自己是分布式系统专家）

### 4. 抽样后的解读

**不要直接给评分**。把答题表现转化成对水位评估的修正：

```
用户在 GPU 架构上自述 L4。
抽样问题："SM 里 warp scheduler 大概的工作机制？"
用户回答：[内容]

→ 解读模板：
   答得自如 + 命中关键点：印证 L4，可能更高
   答得对但生硬：L4 偏低，鲜度有问题（可标注"知识在但需要重新激活"）
   答错或闪躲：L4 不到，下调到 L3
```

**告诉用户抽样的结果时要克制**——不要说"你答错了"，说"这一题答得偏粗——结合你的时间距离，我把这一段的水位标注为'有但需要复盘'"。

## 文件结构

```
knowledge_probes/
├── README.md                    # 你正在读的这个文件
├── _template.md                 # 添加新领域时复制这个模板
├── gpu_soc_architecture.md      # GPU / SoC 架构问题库（示例）
├── ai_engineering.md            # AI 工程化问题库
├── frontend.md                  # 前端问题库
├── backend.md                   # 后端问题库
├── distributed_systems.md       # 分布式系统问题库
├── data_engineering.md          # 数据工程问题库
└── [add more...]
```

**每个领域文件独立。** 添加新领域时：
1. 复制 `_template.md` 改名为 `<领域名>.md`
2. 填充该领域的问题（按时间距离分级）
3. **不需要修改主 SKILL.md**——只需要在使用时按需加载

## 如何添加新问题

每个领域文件按这个结构组织：

```markdown
# [领域名] 知识抽样

## 该领域的"鲜度衰减曲线"
[这个领域哪些知识衰减快、哪些衰减慢]

## L3 级问题（验证"做过"）
[列 5-10 题]

## L4 级问题（验证"懂为什么"）
[列 5-10 题]

## L5 级问题（验证"知道自己不知道什么"）
[列 3-5 题]

## 时间距离调整规则
[针对该领域，远期 / 中期 / 近期分别问什么]
```

## 迭代历史

每个文件应该记录最近一次更新的日期 + 谁更新的 + 改了什么。问题库的演进本身就是 skill 的成长。

每次「问心」运行时，发现某个领域的问题库**不够好**或**缺失**，应该在最终输出后**告诉用户**：「这次评估你的 [领域 X] 时，我发现问题库里这个领域的覆盖偏弱。如果你愿意，我们可以一起补充几道题，下次评估就更准。」

这是「问心」自我迭代的核心机制。

## 重要观察：元认知抽样 > 技术细节抽样

**实测发现**：相比直接问技术 spec / 实现细节，**问"你不知道什么"这一类元认知题，对识别真伪 L4-L5 的精度高得多**。

理由：
- 技术细节题考的是**记忆力**——离开领域 N 年的真专家可能也答不出具体 spec，但这不能否定 ta 的能力
- 元认知题考的是**认知地图**——一个真在 L4-L5 的人，**就算离开 5 年**也能精准说出"我不知道 X、Y、Z"，这种结构化的认知边界陈述伪造不了
- 一个回答如果**精准命中该领域当前最热的研究方向**（即便是用"我不确定 X"的形式），本身就证明 ta 的认知地图是**当前的、精确的**

**实操原则**：
- **优先问 L5 的元认知题**（"你不知道什么"、"反例"、"认知边界"）
- **次选 L4 的判断题**（"为什么是 X 不是 Y"、"什么场景适合 A 不适合 B"）
- **最后才问 L3 的实现题**（具体 API / spec）—— 而且只对**近期接触**的人问
- **几乎不问 spec / 数字** —— 这测的是记忆力，不是能力

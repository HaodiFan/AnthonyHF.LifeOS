# IPO-Reverse 需求规格书

> 本文档由 neil-skills-creator 阶段一产出，用于交接给 skill-creator 进行技术实现。

---

## 1. 概述

| 字段 | 内容 |
|------|------|
| Skill 名称 | `ipo-reverse` |
| 一句话定位 | 从任意产出物逆向萃取教科书级别的 IPO 链路，让小白也能复现高手的产出过程 |
| 目标用户 | Neil 本人（知识萃取）、团队成员（照着执行）、Skill 设计者（转化为 Skill 蓝图） |
| 使用频率 | 高频原子能力——每次做完重要产出都会用、设计新 Skill 时必用、团队培训时必用 |

---

## 2. 问题定义

| 问题 | 回答 |
|------|------|
| 要解决什么问题 | 高手做事的过程是隐性知识，无法直接传递。产出物只展示结果，不展示路径。 |
| 现状痛点 | ① 隐性知识无法传递：高手做完了别人跟不了；② 拆解颗粒度不对：太粗没法执行，太细成碎片；③ 忽略动态判断：传统 SOP 是线性的，真实任务有大量条件分支；④ 一口气 vs 分步分不清：混在一起就没法教别人 |
| 期望效果 | 给定任何产出物，输出一份小白拿着就能照做的 IPO 拆解——清楚标注固定步骤/动态触发/自适应，区分一口气生成和分步执行的边界，复杂度自适应 |

---

## 3. 触发设计

### 3.1 典型触发短语

1. "帮我拆解一下这个东西是怎么做出来的"
2. "逆推一下这个产出物的 IPO"
3. "把这个方案的制作过程拆解出来"
4. "萃取一下这个产出物的知识"
5. "这个东西怎么做的？帮我拆成步骤"
6. "分析一下这个输出的生产流程"
7. "我想把这个过程变成 SOP"
8. "帮我做知识萃取"
9. "逆向分析这个产出物"
10. "拆解这个任务的执行路径"

### 3.2 不应触发的场景

1. "帮我审查这份文档的质量" — 原因：审查质量是评价，不是逆向拆解过程
2. "总结一下这篇文章的要点" — 原因：总结是提取内容，不是还原生产过程
3. "帮我优化这个方案" — 原因：优化是正向改进，不是逆向分析
4. "帮我写一个类似的东西" — 原因：是创作任务，不是拆解任务（但拆解结果可以作为创作的前置步骤）

### 3.3 Description 草稿

> 从任意产出物（文档、方案、代码、对话记录、系统设计）逆向拆解出完整的 IPO 链路（Input-Process-Output）。萃取隐性知识为教科书级别的可复现步骤，区分固定步骤/条件触发/自适应环节，标记一口气生成 vs 分步执行的边界。适用于知识萃取、SOP 制作、Skill 设计蓝图、团队培训材料。当用户说"拆解过程"、"逆推 IPO"、"知识萃取"、"怎么做出来的"、"变成 SOP"时触发。不处理文档审查、内容总结或方案优化。

## 4. 输出物定义

| 输出物 | 格式 | 使用者 | 业务用途 |
|--------|------|--------|---------|
| IPO 拆解文档 | 结构化 Markdown | Neil / 团队成员 / Skill 设计者 | 复现产出过程 / 转化为 Skill / 培训材料 |

### 中间层

| 中间产物 | 用途 | 是否需要用户确认 |
|---------|------|-----------------|
| 初始过程假设（Phase 1 输出） | 粗粒度过程模型 + 产出物视图，让用户校准大方向 | 是——核心交互环节 |
| 深入推导结果（Phase 2 循环中） | 每个阶段的详细步骤 + 动态标记，边推导边验证 | 循环内持续校准 |

### IPO 拆解文档结构

```markdown
# [产出物名称] — IPO 拆解

## 概览
- 产出物类型：[文档/代码/系统/...]
- 复杂度评级：[简单/中等/复杂]
- 总步骤数：X 步（分 Y 个阶段）
- 动态步骤占比：Z%

## 一、Input 清单
### 必需输入
- [输入项]：[说明] — [来源]
### 可选输入
- [输入项]：[说明] — [有则更好，无也能做]
### 动态输入
- [输入项]：[说明] — [过程中可能需要获取，触发条件：...]

## 二、双视图

### 产出物视图（是什么）
产出物由以下模块组成：
| 模块 | 作用 | 由哪个过程阶段产出 |
|------|------|------------------|
| [模块A] | ... | 阶段 2 + 阶段 3 |
| [模块B] | ... | 阶段 1 + 阶段 3 |

### 过程视图（怎么做的）
制作过程分以下阶段：
| 阶段 | 名称 | 类型 | 生成模式 | 产出了哪些模块 |
|------|------|------|---------|--------------|
| 1 | ... | [固定] | [一口气] | 模块A基础 + 模块B基础 |
| 2 | ... | [条件触发] | [分步] | 模块A深化 |

> 注意：产出物结构 ≠ 过程结构。一个过程阶段可能同时产出多个模块的内容，一个模块的内容可能跨多个阶段完成。

## 三、Process 拆解

### 阶段 1：[名称]
**类型**：[固定] / [条件触发：触发条件] / [自适应：触发信号]
**生成模式**：[一口气生成] / [分步执行]
**产出模块**：[对应产出物视图中的哪些模块]

**步骤**：
1. **[步骤名]**
   - 输入：...
   - 操作：...
   - 输出：...
   - 关键判断：[如有决策点，说明判断依据]

2. **[步骤名]**
   - ...

**本阶段质量检查**：[怎么判断这个阶段做对了]

### 阶段 2：[名称]
...

## 四、Output 验证
### 还原检查
- [ ] 按过程视图从头走一遍，能否还原出产出物视图中的所有模块
### 完整性检查
- [ ] 所有 Input 都有来源
- [ ] 所有步骤的输出都被下游消费
- [ ] 产出物视图的每个模块都有对应的过程阶段
- [ ] 过程视图的每个阶段都有对应的产出模块（无孤立步骤）
### 可执行性检查
- [ ] 不了解背景的人能否独立执行
- [ ] 可能卡住的地方已补充说明

## 五、假设与置信度
| 假设内容 | 置信度 | 影响范围 | 验证方式 |
|---------|--------|---------|---------|
| [假设1] | 高/中/低 | [影响哪些步骤] | [怎么验证] |
```

## 5. 工作流程

### 5.1 流程总览

核心架构：**假设驱动的迭代循环**，不是线性管道。

```
Phase 0：信息收集与假设建立
  0a 初始扫描 → 产出物类型判断 + 复杂度初评
  0b 信息缺口识别 → 标记 [已知] / [可推断] / [未知]
  0c 定向提问 → 带假设的验证式提问（非开放式）
  0d 假设确认 → [信息充分] 进入 Phase 1 / [不足] 再问（最多3轮）
    ↓
Phase 1：观察与假设
  1a 建立产出物视图
     · 识别产出物类型与边界
     · 功能分解 → 拆成独立模块/块
     · MECE 校验 → 不重不漏
  1b 形成过程假设
     · "我认为这个产出物是这样做出来的"
     · 输出粗粒度过程模型（3-5 个阶段）
     · 初步建立产出物视图 ↔ 过程视图的映射
  1c 输出理解 + 引导用户校准（核心交互环节）
     · 对整体过程假设，输出 Agent 的理解：
       "我对这个产出物的理解是——
        它由 A、B、C 三个模块组成
        我推测制作过程大致是：先做 X → 再做 Y → 最后 Z
        其中 X 同时产出了 A 和 B 的基础内容"
     · 引导策略：
       ① 给选项而非开放题
         "这部分是先有框架再填内容，还是边写边成型的？"
       ② 用反例激发回忆
         "如果没有做 X，这部分还能做出来吗？"
       ③ 用极端假设暴露隐性步骤
         "让一个完全不懂的人来做，第一个会卡在哪里？"
       ④ 用 Agent 的错误理解触发纠正
         "我猜这部分是一口气写的——如果不是，中间断在哪？"
     · 用户校准后修正过程假设
  输出：经用户校准的粗粒度过程模型 + 产出物视图
    ↓
Phase 2：深入推导与验证（循环）
  ┌→ 2a 对每个阶段深入拆解
  │    · 倒推：直接输入、具体操作步骤、关键决策点
  │    · 同步标记动态类型：[固定] / [条件触发] / [自适应]
  │    · 同步标记生成模式：[一口气生成] / [分步执行]
  │    · 对 [条件触发] 写明触发条件
  │    · 对 [自适应] 写明触发信号 + 调整动作
  │
  │  2b 更新产出物视图 ↔ 过程视图映射
  │    · 这个阶段的步骤产出了哪些模块的内容？
  │    · 有没有跨模块的步骤（如"交叉校验"）？
  │
  │  2c 验证：这个模型能解释产出物的所有部分吗？
  │    · 产出物视图中每个模块都有对应的过程阶段？
  │    · 过程中每个步骤的输出都被下游消费了？
  │    · 有没有"解释不了"的部分？
  │      → 有 → 修正模型，回到 2a
  │      → 无 → 进入 Phase 3
  │
  │  ⚡ 信息缺口触发器（任意时刻）：
  │    推导中发现无法确定的环节 →
  │    影响可信度 → 暂停，定向追问用户
  └──  不影响 → 标记 [假设] 继续
    ↓
Phase 3：形式化与闭环验证
  3a 粒度校准与分层
     · 复杂度评级：简单（≤5步）/ 中等（6-15步）/ 复杂（>15步）
     · 应用 Miller's Law 分层：
       第一层：阶段概览（3-7 个阶段）
       第二层：每个阶段展开为具体步骤
       第三层（复杂任务才需要）：操作级细节
     · 粒度自检：
       每个步骤描述是否只包含一个动作？
       有没有"然后""并且"等连接词需要拆分？
       小白能否不问问题直接执行？
  3b 正向还原验证
     · 从 Input 出发按 Process 走一遍，能否还原出 Output？
     · 如有断裂点 → 回 Phase 2 修正（不是打补丁）
  3c 完整性检查
     · 所有 Input 都有来源？
     · 产出物视图每个模块都有对应过程阶段？
     · 过程视图每个阶段都有对应产出模块？（无孤立步骤）
  3d 假设审计
     · 汇总所有 [假设] 标记，评估置信度
     · 高影响 + 低置信度的假设 → 最后一次追问机会
  3e 可执行性检查
     · 不了解背景的人能否独立执行？
     · 哪里会卡住？补充说明
  输出：验证通过的最终 IPO 拆解文档
```

### 5.2 确认点设计

| 确认点 | 位置 | 确认内容 | 确认方式 | 触发条件 |
|--------|------|---------|---------|---------|
| C0 | Phase 0d 后 | 信息收集是否充分，初始假设是否合理 | 展示假设清单 | 总是触发 |
| C1 | Phase 1c | 产出物视图 + 粗粒度过程假设是否准确 | 输出理解 + 引导式提问 | 总是触发（核心交互） |
| C2 | Phase 2 循环中 | 每个阶段的深入拆解是否准确 | 输出阶段拆解 + 校准提问 | 按需（置信度低时触发） |
| C3 | Phase 3 后 | 最终拆解文档是否准确可用 | 展示完整文档 | 总是触发 |

### 5.3 异常处理

| 异常情况 | 处理方式 |
|---------|---------|
| 产出物极简单（一步能完成） | Phase 1 判断���直接输出简版，跳过分层 |
| 产出物极复杂（>30 步） | 强制分三层，第一层不超过 7 个阶段 |
| 用户给的是"任务描述"而非"产出物" | Phase 0 识别后提示：切换为正向设计模式，或要求用户提供产出物 |
| 拆解过程中发现产出物本身有缺陷 | 标记问题，继续拆解，在验证环节汇总报告 |
| 3 轮提问后信息仍不充分 | 标记所有 [假设]，输出"最佳推测版本"，注明置信度 |
| 用户无法回答引导提问 | 切换提问策略（选项→反例→极端假设），仍无法回答则标记 [假设] |
| Phase 3b 正向还原失败 | 不打补丁，回 Phase 2 修正过程模型 |
| Phase 2 循环超过 3 轮仍不收敛 | 输出当前最佳版本，标注不收敛的原因和待验证点 |

## 7. 成功标准

### 输出质量标准

- [ ] 每个步骤只描述一个动作（无"然后""并且"连接词）
- [ ] 每个步骤标注了动态类型 [固定]/[条件触发]/[自适应]
- [ ] 每个 [条件触发] 步骤有明确的触发条件
- [ ] 每个 [自适应] 步骤有明确的触发信号和调整动作
- [ ] 所有 Input 都有明确来源
- [ ] 所有步骤的输出都被下游步骤消费（无孤立步骤）
- [ ] 第一层阶段数 ≤ 7（Miller's Law）
- [ ] 基于推断的内容标记了 [假设] 和置信度
- [ ] 标注了 [一口气生成] vs [分步执行] 的边界
- [ ] 产出物视图和过程视图之间有明确映射（每个模块追溯到过程阶段，每个阶段标注产出模块）
- [ ] 过程视图中跨模块的步骤（如调研、校验）被正确识别，不被人为拆散到各模块

### 自检规则

Skill 执行完毕后，自动检查：

1. **正向还原测试**：从 Input 出发按 Process 走一遍，能否逻辑上还原出 Output？如有断裂点，标注并补充
2. **完整性测试**：有没有步骤的输入来源不明？有没有步骤的输出无人消费？
3. **可执行性测试**：有没有步骤描述模糊到"不同的人会有不同理解"？如有，拆分或补充说明
4. **粒度一致性**：同一层级的步骤粒度是否大致一致？（不会一个步骤是"打开文件"，另一个是"完成整个分析"）

## 8. 边界与约束

**能做**：
- 从文档、方案、代码、对话记录、系统设计等任意产出物逆向拆解 IPO
- 处理简单到复杂的各种产出物，自适应粒度
- 识别并标记动态步骤（条件触发、自适应）
- 通过引导提问萃取用户的隐性知识
- 标记假设和置信度，区分确定事实和推测

**不能做**：
- 不做产出物的质量评价（好不好不是这个 Skill 的事）
- 不做正向的方案设计（只做逆向拆解）
- 不替用户做决策（只呈现拆解结果）
- 不保证在用户完全无法提供信息时输出高置信度结果

**依赖/前提**：
- 用户需要提供产出物本身（文本、文件、链接等）
- 产出物的创作者最好在场（能回答引导提问），否则输出为"最佳推测版本"

## 9. 测试策略

### 正常场景

| 测试用例 | 输入 | 期望输出 |
|---------|------|---------|
| 拆解一份商业方案 | 一份完整的项目方案文档 | 3-5 个阶段的 IPO 拆解，包含调研/框架设计/内容填充/审校等步骤，标注哪些是一口气写的 |
| 拆解一段 Claude 对话产出 | 一段 Claude 生成的复杂输出 | 识别出 prompt 设计、上下文加载、多轮迭代等步骤，标注动态触发点 |
| 拆解一个简单任务 | 一封邮件回复 | 简版拆解（≤5步），不过度分层 |

### 边缘场景

| 测试用例 | 输入 | 期望行为 |
|---------|------|---------|
| 用户只给了半成品 | 一份未完成的文档 | 识别已完成部分和未完成部分，只拆解已完成部分，标注未完成部分 |
| 用户给的是任务描述不是产出物 | "帮我拆解怎么做一个 landing page" | 识别输入类型，提示用户提供产出物，或切换为正向设计模式 |
| 用户无法回答任何引导提问 | 对所有提问回答"不知道" | 3轮后输出最佳推测版本，所有关键步骤标记 [假设] |
| 极复杂产出物 | 一个完整的系统架构文档（50+页） | 强制三层分层，第一层 ≤7 阶段，可分模块逐步拆解 |

### 不应触发场景

| 测试用例 | 输入 | 期望行为 |
|---------|------|---------|
| "帮我总结这篇文章" | 总结请求 | 不触发本 Skill |
| "帮我改进这个方案" | 优化请求 | 不触发本 Skill |
| "审查一下这个文档有没有问题" | 审查请求 | 不触发本 Skill |

## 方法论决策附录

本 Skill 的流程设计基于以下方法论选择（详见阶段一方法论拆解备忘录）：

| 核心任务 | 方法论 | 在流程中的体现 |
|---------|--------|--------------|
| 信息充分性评估 | 苏格拉底提问 + 假设驱动分析 | Phase 0：先形成假设，再定向提问验证 |
| 解构产出物 | 功能分解 + MECE | Phase 1a：建立产出物视图（模块结构） |
| 逆向推导过程 | 认知任务分析（CTA） | Phase 1b-1c + Phase 2：形成过程假设 → 引导校准 → 深入推导 → 迭代验证 |
| 标记动态性 | BPMN 网关分类模型 | Phase 2a：推导步骤时同步标记固定/条件触发/自适应 |
| 粒度校准 | Miller's Law + 分层递进 | Phase 3a：≤7 阶段 + 按复杂度分层 |

### 架构决策说明

本 Skill 采用**假设驱动的迭代循环**架构，而非线性管道，原因：

1. **产出物结构 ≠ 过程结构**：产出物的模块划分和制作过程的阶段划分是两个独立维度，通过"双视图 + 映射"解决
2. **动态标记不应独立为 Phase**：判断步骤是固定还是动态的，和推导步骤本身是同一个思考过程，合并到 Phase 2 中同步完成
3. **验证内嵌而非末尾**：Phase 2 的循环中持续验证"模型能否解释产出物所有部分"，而非做完全部再验证。Phase 3b 做最终正向还原时，如果失败则回 Phase 2 修正模型，不打补丁

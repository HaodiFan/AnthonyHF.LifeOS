# 完成度评估详细规则

阶段 1.7 用。这是「问心」最有差异化的一层——把"我现在的能力 vs 这个领域的完整版"显式化。

## 核心机制：三步走

### Step 1：定义"100%"

**核心要求**：100% 必须**显式列出**。不能藏起来，不能含糊。

理由：用户必须看到"100% 长什么样"才能判断百分比是否合理，也才能对剩余的部分有具象认知。

**做法**：

1. 调用 `web_search` 查询该领域的：
   - 顶级公司的相应岗位 JD
   - 顶级学术会议 / 期刊（如果是研究领域）
   - 行业内被公认的 L5 标杆人物（不是 LinkedIn 上的"专家"，是行业内提起来"啊那个 X"的人）
2. 提取出"完整版能力"的 5-10 个支柱
3. 每个支柱标注**默认粒度（B 粒度）**

**默认粒度示例**（数据获取领域）：

```
数据获取（完整版定义）

100% = 完整覆盖以下 5 个支柱：
1. 爬虫
   - RPA 模拟
   - 逆向（网页 / 桌面应用 / 手机 app）
2. API 集成
   - REST / GraphQL / WebSocket
   - 鉴权（OAuth / JWT / Session）
3. 数据库直连
   - 关系型直连
   - 数据仓库 / 数据湖
4. 第三方数据源采购
   - 公开数据集
   - 商业数据 API
   - 数据交易平台
5. 埋点 / 日志采集
   - 前端埋点
   - 后端埋点
   - 日志聚合系统

参考标杆：[从 web_search 来的具体公司 / 人物]
```

**用户接受深入时（C 粒度）**：每个 B 粒度叶子下再展开一层到具体技术栈，例如：

```
1.2 逆向 / 网页
    ├── HTTP 协议层抓包分析（Charles / Fiddler / mitmproxy）
    ├── JS 逆向（混淆解密 / AST 还原 / WASM 分析）
    ├── 反爬绕过（设备指纹 / 滑块 / TLS 指纹 / Cloudflare 5s）
    ├── 浏览器自动化（Playwright / Puppeteer / Selenium）
    └── 大规模代理池与调度
```

---

### Step 2：在每个支柱上打分

**两个维度独立打分**：实现层 + 元认知层。

**广度优先，深度修饰**：每个支柱先看用户**覆盖了多少子项**（广度），再标记每个子项的**水位**（深度）。

```
支柱 N · [名称]

子项 1     ✅ (实现 L4, 元认知 L4)   [证据]
子项 2     ✅ (实现 L3, 元认知 L4)   [证据]
子项 3     ⬜ L0                    （空白）
子项 4     ⬜ L0                    （空白）

广度覆盖率：50%（2/4）
已覆盖部分平均水位：实现 L3.5 / 元认知 L4

支柱完成度（加权）：约 45%
```

**加权公式**（参考）：
```
支柱完成度 = 广度覆盖率 × 0.6 + 已覆盖平均水位标准化 × 0.4
其中"水位标准化" = 平均 L 值 / 5
```

例如上面：50% × 0.6 + (3.75/5) × 0.4 = 30% + 30% = **60%**...

但这只是参考公式。**最终百分比应该让 Claude 综合判断后给出诚实的数字**——重要的不是公式精确性，是数字背后的**解读**。

---

### Step 3：智能解读（最重要的一步）

光给数字没用。必须回答**三个问题**：

#### 问题 1：剩余的 % 里，哪些是"必须补的"，哪些"可以不补的"？

依据是**用户的方向**（创业 CTO / 进大厂 / 学术 / 转赛道）。同样的空白对不同方向价值完全不同。

输出格式：

```
剩余 33% 的成分分析：

必须补的（约占剩余的 60%）：
- [具体支柱]：理由 [因为你的方向是 X，这块是核心依赖]

可以不补的（约占剩余的 40%）：
- [具体支柱]：理由 [虽然 100% 定义里有，但对你的方向影响小]

按必须补的部分计算，"实质完成度" ≈ XX%
```

#### 问题 2：已有的 % 里，哪些是"特别稀缺的"？

这才是真壁垒。要把它**显式拎出来**，因为这是 BP 卖点的核心证据。

输出格式：

```
已有的 67% 里，特别稀缺的部分：

⭐⭐ 顶级稀缺：
- [具体支柱组合]
  稀缺性：全球做这个组合的人以"百"计
  来源：[哪些具体经历沉淀出来的]

⭐ 稀缺：
- [具体支柱]
  稀缺性：[具体描述]
```

#### 问题 3：1000 小时投资建议

**给具体可执行的建议**——这是用户最实际能用上的部分。

输出格式：

```
如果只能投资 1000 小时再学习，最该补：

首推：[具体支柱 X]
- 理由：[为什么这个最值得 / ROI 最高]
- 起点：[从哪里开始学，具体到资源 / 课程 / 项目]
- 里程碑：[1000 小时后能达到什么水位]

次推：[具体支柱 Y]
- ...

不推荐补的：[具体支柱 Z]
- 理由：[为什么不补]
```

## 重要原则

### 1. 百分比要"诚实地保守"

宁低估不高估。一个老实的 60% 比一个虚的 80% 有用。**虚高百分比是用户体验灾难**——用户会觉得"那我已经够厉害了"，从而停止成长。诚实的低估反而会激发用户的成长动力。

### 2. 完成度 ≠ 价值

明确告诉用户：

> 60% 不代表你不行——很多 L5 级别的人在自己的细分领域只有 60%，因为 ta 专精的恰好是最稀缺的 60%。完成度的"低"反而可能是好事——意味着 ta 选择了"窄而深"的路径。

防止百分比被错误解读为"分数"。**100% 不是目标，搞清自己在 100% 里的位置才是目标**。

### 3. 这个机制只对优势区做

⭐ / ⭐⭐ 优势区做完整 100% 定义 + 评估。
🟡 触及区不做——那些领域用户本来就不打算做到顶。
⬜ 空白区不做——0% 没什么可分析的。

### 4. 元认知 vs 实现要分开看

按 SKILL.md 主文件里的 4 种情况：

| 实现 | 元认知 | 解读 |
|---|---|---|
| 高 | 高 | 真壁垒 |
| 高 | 低 | "假壁垒" —— AI 时代会被废 |
| 低 | 高 | "AI 时代友好的空白" —— 实现可补 |
| 低 | 低 | "真空白" |

输出时**两个维度都要标**——不能只标实现层（那是前 AI 时代的视角）。

### 5. 必须用 web_search 做行业对标

**这是必须的**。没有外部坐标系的水位评估不可信。

最低限度的搜索内容：
- 该细分领域最顶级的 1-2 家公司的相应岗位 JD
- 该领域的主流社区 / 顶级会议
- 近 1 年的领域趋势

把搜出来的内容**显式列入"参考标杆"**，让用户知道百分比是基于什么坐标系。

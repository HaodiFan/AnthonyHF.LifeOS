# RedNote / 小红书 Channel Reference

这个 reference 只处理 RedNote/小红书渠道技巧。它不改变 `public-narrative-system` 的边界：RedNote 是公开叙事系统的一个输出面，不是独立人格，也不是上层 skill。

## 适用场景

- 用户要写 RedNote / 小红书笔记、口播、标题、封面、标签、互动问题、发布包。
- 用户要把某个公开叙事稿件适配成 RedNote 首发。
- 用户要求借鉴小红书平台技巧，但不能牺牲 Anthony 的工程师叙事。

## RedNote 发布包

RedNote-ready draft 不只写正文，应补齐：

1. Primary title：一个可直接发布的标题。
2. Title pool：5-8 个不同角度标题。
3. Cover text：主标题、副标题、期号、侧边标签。
4. Caption / 口播正文：短版或长版正文。
5. Tags：series、concept、audience、product 四类。
6. Interaction prompt：一个能引出真实讨论的问题。
7. Soft CTA：关注系列、留言想看的层、提问，不做强转化。
8. Platform risk scan：平台敏感词、证据敏感、隐私泄露、voice drift、产品过度承诺。
9. Content method mapping：说明正文和发布资产分别对应了哪些方法论模块。

`Content Method Mapping` 推荐格式：

| 结构位置 | 当前具体内容 | 当前表达方式 | 承担作用 | 对应方法论 | 待确认 / 可替换点 |
|---|---|---|---|---|---|
| 封面 / 标题 | 当前主标题、副标题、最大关键词 | 短词、强名词、第一眼可读 | 决定用户是否停下 | 第一眼包装；封面标题方法 | 结构是否保留；关键词和视觉锚点是否要换 |
| 开头 3-5 句 | 当前开头原句或概括 | 直接抛问题 / 先给判断 / 给实验边界 | 给出继续看的理由 | 四维 hook：打断预测 / 奖励期待 / 精准命名 | 结构是否保留；钩子内容和口吻是否替换 |
| 中段真实问题 | 当前场景、痛点、例子 | 具体工作场景，不空讲概念 | 证明内容来自真实实践 | 真实场景 + 可信证据 | 痛点是否真实，是否需要用户补充 |
| 概念命名 / 判断 | 当前命名、判断句 | Anthony 式判断先行，压成一个模型 | 让读者带走一个可复述观点 | 结构化获得感；Anthony voice | 名词是否准、表达是否像 Anthony |
| 产品露出 | 当前产品出现方式 | 从问题自然长出产品层 | 解释产品存在原因 | 产品叙事规则 | 是否硬广，产品关系是否准确 |
| 结尾 / CTA | 当前收束和互动问题 | 短句收束，留下系列记忆点 | 引导评论并记住长期实验 | 互动入口 + 系列化记忆点 | CTA 是否自然，是否需要换问题 |

审稿时优先让用户逐格确认：

```text
结构位置保留 / 替换
当前内容保留 / 替换
表达方式保留 / 改口吻
承担作用是否成立
对应方法论是否认同
```

## RedNote 爆款构成

这里的“爆款构成”不是平台算法承诺，而是内容工程上的高概率结构。对 Anthony 来说，优先追求“可持续被记住”，不是一次性流量话术。

一条 RedNote 内容通常由 8 个层组成：

1. **第一眼包装**：封面 + 标题 + 前 3 秒。决定用户是否停下。
2. **认知钩子**：一句反常识、反身份或反直觉判断。决定用户是否想听完。
3. **真实场景**：一个具体触发点，而不是抽象开题。决定内容是否可信。
4. **身份投射**：让读者知道“这和我有什么关系”。可以是创业者、工程师、AI 使用者、知识工作者。
5. **结构化获得感**：读完至少带走一个模型、判断、方法或命名。
6. **可信证据**：真实实验、过程、失败、纠偏、repo、系统截图、连续记录；不要用伪数据和伪权威。
7. **互动入口**：一个能让评论区沉淀经验的问题，而不是机械刷互动。
8. **系列化记忆点**：让读者知道这不是孤立观点，而是一个长期实验。

Anthony 的 RedNote 内容默认采用这个映射：

```text
第一眼包装 = 封面上直接给判断
认知钩子 = 复刻自己 / 开发公司 / 数字生命不是 chatbot
真实场景 = 创业一年半、做 openLifeOS、一次系统纠偏
身份投射 = 工程师创业者、AI-native 组织实践者、想拥有数字分身的人
结构化获得感 = 生命系统 / 组织系统 / Memory -> Reflection -> Alignment -> Skill -> Evolution
可信证据 = 这是长期实验，不是完成式结论
互动入口 = 让读者回答自己想复刻哪一层
系列化记忆点 = 生命系统实验日记
```

如果一条稿子只有产品名、概念名或愿景，没有真实触发和结构化获得感，就不算 RedNote-ready。

### 爆款口播案例模式：具体场景里的方法跃迁

参考 `AI 做 PPT / PS5 说服老婆` 类案例时，学结构，不学人设。

这类口播的核心不是“幽默案例”本身，而是：

```text
通用承诺
-> 荒诞但具体的生活/工作场景
-> 普通做法
-> 第一次拆任务
-> 吸取高手经验
-> 版本对比
-> 给差异命名
-> 第二次拆任务
-> 再吸取高手经验
-> 第三版效果展示
-> 回到通用方法
```

可复用要点：

- **大承诺先行**：先说学完能获得什么能力，不先介绍工具。
- **具体场景承载抽象方法**：场景要具体、有轻冲突、有可见结果，避免空讲方法论。
- **先给普通版，再给升级版**：第一版“看起来还行，但远远不够”，观众才感知差距。
- **操作感要强**：用“先拆成两步”“注意看”“第二步还有优化空间”“再生成一次”这类推进，让内容像 live demo。
- **差异要命名**：把版本差异压成可记忆概念，让观众感觉拿走了识别框架。
- **最后做目的回收**：告诉观众真正目的不是这个案例，而是背后的通用方法。

对 Anthony 的适配：

```text
普通 AI 使用：
一次性 prompt -> 一次性结果 -> 下一次重新开始

AI-native organization：
一次真实产出 -> memory -> skill -> feedback -> 下一次起点变高
```

Anthony 可以使用“版本对比 + 方法抽象”，但不要照搬家庭玩笑、人设表演、拿捏式表达或未经确认的研究数字。对 Anthony 更合适的差异命名包括：

- `context inheritance`
- `memory density`
- `skill reuse`
- `feedback velocity`
- `autonomous rate`
- `next-run advantage`
- `second derivative moat`

### 爆款开头拆解：四维 hook 检查

让 AI 拆解或生成开头时，不要问“这个开头为什么火”。这通常会得到修辞、叙事、节奏之类的泛分析。

应要求它按四个维度输出可复用句式和证据链：

1. **打断预测**：哪一句让用户觉得“这不对”或“这个答案和我预期不同”。
2. **奖励期待**：哪一句让用户知道继续看能获得一个模型、命名、方法或判断。
3. **损失厌恶**：哪一句让用户觉得不看会错过一个关键变量。
4. **精准命名**：哪一句说出了用户隐约知道但没命名的感受。

每个维度最好让 AI 给 0-10 分，并指出具体字词、句式和逻辑反转，不接受“有反差感”“引发好奇”这类空结论。

对 Anthony 的高抽象内容，推荐开头公式：

```text
高压问题
-> 常见答案
-> 追问一个更高阶变量
-> 给出命名
-> 普通做法 vs 进化做法
-> 回到真实系统实验
```

例子：

```text
你们公司的 moat 是什么？
如果你的答案还是数据、客户、功能，我会追问一句：
你的差距拉开速度，还在加速吗？
我的答案是：moat 是组织进化速度的增长速度。
```

注意：学习的是注意力结构，不要照搬夸张金额、百万播放、冤大头、操控用户这类刺激物。Anthony 的开头要有压强，但不能变成教程号或营销号。

### Anthony 高抽象钩子

Anthony 的钩子不一定要是普通意义上的“反常识”。更适合的结构是：

```text
战略问题直接开场
-> 高抽象判断
-> 先让读者觉得有压强
-> 正文逐步解释
-> 最后落到工程定义
```

例子：

```text
你们公司的 moat 是什么？
-> moat = d²Y/dt²
-> Y 是组织生产力，t 是时间
-> dY/dt 是组织变强速度
-> d²Y/dt² 是变强速度是否还在加速
-> memory / skill / feedback / agent collaboration / autonomous rate 如何互相放大
```

这类钩子要注意：

- 不要写成 `最近有人问我一个问题` 这种铺垫，第一句可以直接是问题本身。
- 第二句应直接给结论：`我认为...` / `我的判断是...`，再展开，不要先解释再倒推出结论。
- 主体只走正向链路：结论 -> 变量 -> 机制 -> 实验；传统定义、免责声明和 fact-check 放到发布边界，不抢正文。
- 不要一开头就把数学概念讲透，否则失去停留感。
- 后文必须 fact-check 并落地，避免变成“听起来很厉害但没有解释”的空话。

### 身份投射：主页关系检查

RedNote 内容不只解决“这一条讲什么”，还要解决观众点进主页后的判断：

```text
这个人和我有什么关系？
平台应该把他推给谁？
我为什么要继续看他的系列？
```

Anthony 的默认关系定位：

```text
工程师创业者 / 系统架构型实验者
正在公开记录如何把自己、公司和数字分身一起工程化。
```

要激活的读者投射：

- 缺 AI-native organization 方向感的人，在这里看到一条工程路径。
- 想用 AI 做真实工作而不是收藏工具的人，在这里看到连续实验。
- 对数字分身/个人知识系统感兴趣的人，在这里看到从“像不像”到“能不能持续进化”的标准。
- 创业者和工程师在这里看到“公司也可以被当成系统开发”。

每条发布包应能回答：

- 这条更适合推给谁？
- 读者在 Anthony 身上看到的是哪种关系：系统架构者、真实实验者、工程化样本，还是产品构建者？
- 这条内容有没有让读者看见自己缺的那一块：方向、方法、系统、勇气或真实样本？

注意：这里学习的是“关系定位”，不是把 Anthony 包装成心理学人设。不要为了原型感增加不真实的脆弱叙事。

## 内容结构

优先使用这个推进顺序：

```text
真实触发场景
-> 反直觉判断
-> 工程化解释
-> 系统结构
-> 产品层只作为系统回应出现
-> 回到长期实验
```

高抽象战略问题类内容可以用这个推进顺序：

```text
战略问题
-> 直接结论
-> 核心变量 / 函数
-> 变量之间如何互相放大
-> 回到真实实验 / 系统动作
-> 长期实验边界
```

不要从产品功能开始。产品出现必须符合：

```text
真实实验 -> 暴露问题 -> 对应产品层 -> 为什么需要这个产品 -> 回到共演化
```

产品露出不要写成清单。尤其是首发内容，产品最好只作为真实实验里的一个系统名、一个承载层或一个自然结果出现。先让读者记住问题和判断，再逐步让产品矩阵长出来。

当前 `生命系统实验日记` 第一集的更优主线：

```text
我在尝试复刻我自己
-> openLifeOS 是这个长期系统的名字
-> 复刻自己让我重新理解公司
-> 公司也需要记忆、Skill、人格和进化机制
-> 我不是在管理公司，我是在开发公司
```

## 标题技巧

标题要制造“认知钩子”，但不能变成夸张承诺。

优先类型：

- 反差：`我不是在管理公司，我是在开发公司`
- 实验记录：`创业一年半笔记：我在开发一家自进化企业`
- 工程视角：`公司，也可以被当成系统来开发`
- 概念重命名：`数字分身不是 chatbot，是长期生命系统`
- 问题反转：`真正难的不是用 AI，而是让组织自己进化`

避免类型：

- `最强 / 第一 / 唯一 / 全网`
- `普通人也能 / 小白必看`
- `X 个神器 / 野路子 / 逆袭指南`
- 没有证据的数字化承诺

## 封面技巧

封面主标题应短，最好 1-2 行，承接核心判断：

```text
我不是在管理公司
我是在开发公司
```

副标题用于解释角度，不要承载太多概念：

```text
以工程师思路重构公司系统
```

### 第一眼包装：封面标题方法

小红书打开第一眼是一堆封面标题，初始点击主要来自用户在这一堆里的选择。很多笔记的数据问题还没到“内容不行”的阶段，封面标题本身就是瓶颈。

封面优化原则：

- 主标题服务点击，不服务完整表达；不要把整套理论塞进封面。
- 关键词要一眼扫到：`moat`、`加速`、`二阶导`、`开发公司`、`openLifeOS` 这类词只选 1-2 个。
- 构图要有差异：使用系列视觉、系统图、知识卡局部或真实工作台截图，避免普通模板感。
- 画面要有可信质感：字体少、层级清楚、主标题优先、背景不抢字。
- 活人感来自真实实验，不必硬套生活博主的自然环境。

Anthony 的 #001 推荐封面结构：

```text
主标题：你们公司的 / moat 是什么？
副标题：差距拉开速度还在加速吗
角标：生命系统实验日记 001
视觉：系列封面原型 + 系统图/知识卡局部
```

期号只跟真实发布顺序走。开场、预告、置顶稿不自动占用 `#001`。

## 互动与 CTA

互动问题要让评论区沉淀真实经验，不做机械刷互动。

推荐：

```text
你觉得一家公司最像“系统 bug”的问题是什么：信息断层、经验无法复用，还是老板不推就停？
```

Soft CTA 推荐：

```text
后面我会继续记录这个系统怎么搭、哪里失真、哪里需要重新蒸馏。想看哪一层，可以直接留言。
```

避免：

- `评论区扣关键词`
- `私信我`
- `加微信`
- `限时福利`
- `主页领取`

## 发布前检查

RedNote publish-ready 前运行：

```bash
node scripts/check-rednote-risk.mjs drafts/active/<draft>.md
```

运行风险检查前先做 Anthony humanizer pass：

```text
删填充
-> 查归因
-> 去机械对比和三段式
-> 把变量清单改成系统状态变化
-> 去宣传腔
```

这一步借鉴 `op7418/Humanizer-zh`，但不要把 Anthony 的工程密度改成泛口语。

检查结果是 review signal，不是自动删除指令。遇到误报时，优先调整检查规则，让工具识别“承诺式风险”，不要误伤正常叙述。

重点检查：

- 绝对化 / 广告法风险
- 未证实证明 / 伪权威
- 收益、搞钱、副业、变现表达
- 站外引流
- 客户、会议、营收、ROI、融资、内部路线图
- Anthony voice drift
- AI-writing texture / generic polished style
- 产品过度承诺
